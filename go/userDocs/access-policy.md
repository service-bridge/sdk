# Access Policy

[← к индексу](./index.md)

Политика доступа принадлежит рантайму: оператор ограничивает, что сервис может регистрировать, что он может отправлять и кто может к нему обращаться. SDK политику **не редактирует** — он показывает её результат и даёт на него отреагировать.

## 1. Модель

Политика делится на две стороны:

- **Egress** — что сервис может отправлять: вызвать чужой RPC, опубликовать событие, запустить workflow.
- **Acceptance** — кто может обращаться к нему: чей вызов он принимает, на какие события подписывается, какой workflow ему разрешено обслуживать.

Для RPC рантайм делает **двустороннюю** проверку: вызывающему должно быть разрешено отправить, принимающему — принять. Обе стороны должны разрешать.

Правила и capability-флаги живут в рантайме и редактируются его средствами. В SDK нет ни одной функции, которая их меняет.

## 2. Всё разрешено по умолчанию

Только что созданный сервис не ограничен ничем. Отсутствие правил для пары (сервис, действие) рантайм трактует как разрешение. Ограничения оператор добавляет отдельно.

То же правило действует и на входящем сервере SDK: политика без единого правила приёма означает, что сервис принимает всех.

## 3. Нарушения при старте

Рантайм в первом снапшоте реестра присылает список объявлений, которые политика отвергла. SDK пишет каждое в лог уровня Warn и вызывает колбэк:

```go
func watchPolicy(c *sb.Client) {
	c.OnPolicyViolation(func(v sb.PolicyViolation) {
		log.Printf("policy refused %s %q (side=%s): %s",
			v.Declaration, v.Value, v.DenySide, v.Reason)
	})
}
```

| Поле `sb.PolicyViolation` | Что это |
|---|---|
| `Declaration` | Какое объявление отвергнуто. |
| `Value` | Конкретная цель: имя метода, имя события, имя workflow. |
| `DenySide` | Какая сторона отказала. |
| `Reason` | Человекочитаемое объяснение от рантайма. |

**Это стоит внимания, хотя формально не ошибка.** Рантайм регистрирует, что может, и предупреждает про остальное, поэтому на проводе наполовину подключённый сервис выглядит как здоровый. Колбэк — единственный сигнал, что часть объявлений не работает.

Колбэк вызывается и для отказа по публикации события: [публикация возвращается задолго до отправки](./events.md#10-локальный-outbox), и бросить ошибку вызывающему уже некуда. В этом случае `Declaration` — `"event.publish"`, `Value` — имя события, `DenySide` — `"self_egress"`.

Колбэки выполняются на собственных горутинах клиента и не должны блокировать.

## 4. Строгий режим

```go
func strict(key string) (*sb.Client, error) {
	return sb.New("localhost:14445", key, sb.WithFailOnPolicyViolation())
}
```

`WithFailOnPolicyViolation` превращает предупреждение в остановку: при любом нарушении клиент останавливает сам себя.

Выключено по умолчанию сознательно: сервис, зарегистрировавшийся наполовину, обычно лучше, чем сервис, который не стартовал. В проде, где половина функциональности хуже честного отказа, включайте.

## 5. Чтение текущей политики

```go
func showPolicy(c *sb.Client) {
	p := c.PolicyEvaluation()
	log.Println("capabilities:", p.Capabilities)
	for _, w := range p.Warnings {
		log.Printf("  refused: %s %q — %s", w.Declaration, w.Value, w.Reason)
	}
}
```

`PolicyEvaluation` — последний снапшот, который прислал рантайм. До первого кадра реестра он пустой: ни возможностей, ни предупреждений. Метод безопасен для вызова в любой момент и ничего не блокирует.

Карта сервисов показывает только то, что вам доступно: ваш собственный сервис и те, что вы объявили зависимостями.

```go
func showMap(c *sb.Client) {
	m := c.ServiceMap()
	for _, i := range m.Instances {
		log.Printf("%s/%s at %s status=%s", i.ServiceName, i.InstanceID, i.CallEndpoint, i.Status)
	}
	for _, method := range m.Methods {
		log.Printf("%s.%s type=%s streaming=%v", method.ServiceName, method.Name, method.Type, method.Streaming)
	}
}
```

## 6. Что видит код при отказе

| Где | Что происходит |
|---|---|
| Регистрация обработчика при отключённой возможности | Обработчик **не регистрируется**, но `Start` не падает — сервис остаётся жив. Пропуск приезжает как нарушение в колбэк. |
| Объявление зависимости или подписки, не покрытое правилами | Регистрация проходит, приезжает нарушение. Реальная попытка вызова будет отклонена рантаймом. |
| Исходящий RPC | Ошибка с кодом `CodeAccessDenied` (`errors.Is(err, sb.ErrAccessDenied)`). |
| `c.Workflow.Start` | То же — `CodeAccessDenied`. |
| Публикация события | Ошибка **не** возвращается: публикация уже вернула успех, положив событие в локальный буфер. Строка в буфере помечается провалившейся терминально, без ретраев, и срабатывает `OnPolicyViolation`. |
| Входящий RPC от неразрешённого вызывающего | Ваш обработчик не выполняется; вызывающий получает `CodeAccessDenied`. |

```go
func callGuarded(ctx context.Context, m *sb.Method[*paymentpb.ChargeRequest, *paymentpb.ChargeReply]) error {
	_, err := m.Call(ctx, &paymentpb.ChargeRequest{UserId: "u-1", Amount: 100})
	if errors.Is(err, sb.ErrAccessDenied) {
		log.Println("политика доступа не разрешает этот вызов")
		return nil
	}
	return err
}
```

## 7. Приём вызовов на стороне callee

Входящий сервер SDK сам проверяет вызывающего, а не полагается только на рантайм.

1. Вызывающий опознаётся по **проверенному** клиентскому сертификату: из него читается SPIFFE-идентичность. Вызов без клиентского сертификата или с сертификатом, из которого идентичность не извлекается, отвергается как неаутентифицированный.
2. Опознанный вызывающий проверяется по правилам приёма. Отсутствие правил — разрешение. При отказе вызывающий получает `CodeAccessDenied`.

Вызов от самого рантайма (транспорт `TransportProxy`) проходит: двусторонняя проверка к этому моменту уже сделана на его стороне.

Проверка приёма выполняется **до** взятия слота конкурентности: вызывающий, которого никто не пускает, не должен занимать слот, за который стоят в очереди допущенные.

На прямом пути (`TransportDirect`) есть ещё одна проверка, уже на стороне вызывающего: SDK требует, чтобы сертификат того, к кому он подключился, нёс SPIFFE-идентичность именно того инстанса, к которому он шёл. Без этого любой сервис mesh мог бы выдать себя за любой другой — все листовые сертификаты подписаны одним CA, и одной проверки цепочки недостаточно.
