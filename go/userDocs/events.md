# Events

[← к индексу](./index.md)

Durable publish/subscribe с доставкой at-least-once. Публикация возвращается, когда рантайм сохранил событие; доставка подписчикам — асинхронная.

## 1. Краткая модель

```
publish                                       deliver
────────                                      ────────
sb.PublishEvent → очередь в памяти            рантайм → стрим Subscribe
       ↓ отправитель                                   ↓
   Events.Publish → вердикт рантайма          обработчики совпавших шаблонов → ack / nack
       ↓
   PublishEvent возвращает id
```

`PublishEvent` возвращает идентификатор, когда рантайм подтвердил событие — к этому моменту оно лежит в его хранилище. Пока рантайм недоступен, событие ждёт в очереди в памяти; очередь ограничена по размеру (`CodeQueueFull`), ожидание — по времени (`CodeTimeout`). На диск SDK ничего не пишет: неподтверждённое событие умирает вместе с процессом.

## 2. Объявление события

```go
func declarePlaced(c *sb.Client) (*sb.Event[*orderpb.OrderPlaced], error) {
	return sb.DefineEvent[*orderpb.OrderPlaced](c, "order.placed")
}
```

`DefineEvent` объявляет событие, которое сервис публикует, и замораживает его схему — она выводится из protobuf-дескриптора типа. Возвращённый `*sb.Event[T]` — типизированная ручка публикации. Это объявление только публикующей стороны: подписчику `DefineEvent` не нужен.

Объявлять нужно **до** `Start`; позже — `CodeState`.

### Имя события

Имя должно подходить под `^[a-z0-9_-]+(\.[a-z0-9_-]+)*$` — сегменты из строчных букв, цифр, подчёркиваний и дефисов, разделённые точками. Правило то же, что у рантайма, и проверяется локально: неподходящее имя отвергается при объявлении с `CodeInvalidEventName`, а не после круга по сети.

Подстановочные знаки в **публикуемом** имени недопустимы — публикуется всегда конкретное событие.

## 3. Подписка

```go
func subscribeShipped(c *sb.Client) error {
	return sb.SubscribeEvent(c, "order.shipped",
		func(ctx context.Context, e *orderpb.OrderShipped) error {
			return handleShipment(ctx, e.GetOrderId(), e.GetCarrier())
		})
}
```

Тип события выводится из функции: payload декодируется в собственный тип подписчика. Подписываться нужно до `Start`, иначе `CodeState`.

**Один шаблон — один обработчик на процесс.** Второй обработчик того же шаблона — `CodeValidation` при объявлении. Несколько обработчиков на одно событие получаются разными шаблонами (`order.placed` и `order.*`).

### Шаблоны

Подписка, в отличие от публикации, принимает шаблон:

```go
func subscribeFamily(c *sb.Client) error {
	return sb.SubscribeEvent(c, "order.*",
		func(ctx context.Context, e *orderpb.OrderPlaced) error {
			return audit(ctx, e.GetOrderId())
		})
}
```

| Знак | Что покрывает |
|---|---|
| `*` | ровно один сегмент |
| `#` | ноль или больше сегментов |

Неподходящий шаблон отвергается при объявлении с `CodeInvalidEventName`.

Маршрутизацией занимается рантайм: он сопоставляет имя опубликованного события с шаблонами подписчиков и перечисляет в доставке те шаблоны, которые совпали. SDK запускает обработчики ровно этих шаблонов, каждый один раз, и подтверждает доставку, только если все они вернули `nil`. Своего сопоставления шаблонов у SDK нет.

Доставка несёт **конкретное** имя, которое использовал публикующий. Обработчик получает уже декодированный payload; если под шаблон попадают события с разной формой payload'а, декодирование в один тип неминуемо сломается — для такого случая есть `sb.SubscribeEventRaw`.

### Недекодированный payload

```go
func subscribeRaw(c *sb.Client) error {
	return sb.SubscribeEventRaw(c, "audit.#",
		func(ctx context.Context, payload []byte) error {
			return archive(ctx, payload)
		})
}
```

Это способ обслужить имя, у которого форма payload'а зависит от публикующего, — ни один параметр типа такое не описывает.

### Фильтр

```go
func subscribePaidEU(c *sb.Client) error {
	return sb.SubscribeEvent(c, "order.placed",
		func(ctx context.Context, e *orderpb.OrderPlaced) error {
			return bookShipment(ctx, e.GetOrderId())
		},
		sb.WithFilter(map[string]any{"$.status": "paid", "$.region": "eu"}))
}
```

`sb.WithFilter` сужает подписку на стороне рантайма: доставляются только события, у которых в JSON-payload каждый указанный путь равен своему литералу. Фильтр вычисляет рантайм по JSON-зеркалу payload'а; SDK его только передаёт. Фильтр, который рантайм не принял, отвергает регистрацию, и клиент останавливается.

### Доставка без обработчика

Если ни один из совпавших шаблонов в процессе не обслуживается, доставка отклоняется с причиной `no handler for matched patterns`.

## 4. Публикация

Публиковать можно только **после** `Start`; раньше — `CodeState`.

```go
func publishPlaced(ctx context.Context, placed *sb.Event[*orderpb.OrderPlaced]) (string, error) {
	return placed.Publish(ctx,
		&orderpb.OrderPlaced{OrderId: "o-1", Total: 4200, UserId: "u-1"},
		sb.WithPartitionKey("o-1"),
		sb.WithEventIdempotencyKey("order-o-1-placed"),
	)
}
```

Возвращается идентификатор события — UUIDv7, возрастающий в порядке публикации. Публикуется всегда имя, а не шаблон.

Без объявленной ручки — то же самое свободной функцией:

```go
func publishDirect(ctx context.Context, c *sb.Client) (string, error) {
	return sb.PublishEvent[*orderpb.OrderPlaced](ctx, c, "order.placed",
		&orderpb.OrderPlaced{OrderId: "o-2", Total: 900, UserId: "u-2"})
}
```

## 5. PublishOption

| Опция | По умолчанию | Что делает |
|---|---|---|
| `WithEventIdempotencyKey(k)` | нет | Ключ дедупликации на стороне рантайма: повтор с тем же ключом возвращает id исходного события. Назван отдельно от `WithIdempotencyKey`, потому что эти два ключа едут в разные места. |
| `WithPartitionKey(k)` | нет | FIFO-дорожка: события с одним ключом видны потребителям в порядке публикации. |
| `WithFireAndForget()` | выключено | Вернуть id сразу после постановки в очередь, не дожидаясь подтверждения рантайма. См. [§9](#9-без-ожидания). |
| `WithHeaders(map[string]string)` | нет | Метаданные конверта. |
| `WithOccurredAt(unixMs)` | момент публикации | Когда событие произошло, в unix-миллисекундах. |

## 6. Гарантии доставки

**At-least-once.** Обработчик обязан быть идемпотентным.

- Возврат `nil` из обработчика подтверждает доставку.
- Возврат ошибки отклоняет её, и рантайм доставит событие позже.
- Паника обработчика превращается в отклонение с причиной, а не роняет процесс.
- Ретраи, веерная рассылка и dead-letter — за рантаймом.

Одновременно обрабатываемых доставок не больше `WithMaxInFlightEvents(n)` (по умолчанию 32). Это настоящий backpressure: на пределе SDK перестаёт вычитывать стрим доставок, и рантайм это чувствует.

Контекст обработчика несёт трассировку публикующего, поэтому вызовы изнутри обработчика попадают в то же дерево трейса. `Stop` ждёт работающие обработчики до своего дедлайна, а после него отменяет их контекст.

`sb.DeliveryFromContext(ctx)` возвращает `sb.DeliveryInfo`:

| Поле | Что это |
|---|---|
| `EventID` | Идентификатор события. |
| `EventName` | Конкретное имя, под которым событие опубликовано. |
| `Attempt` | Номер попытки доставки. |
| `DeliveryID` | Идентификатор доставки. |
| `LeaseToken` | Непрозрачное поколение доставки. Это не гарантия бизнес-идемпотентности. |
| `PartitionKey` | Ключ партиции события; пусто, если его нет. |
| `Headers` | Заголовки конверта из `WithHeaders`. |
| `OccurredAtMs` | Когда событие произошло, unix-мс. |

## 7. Идемпотентность

Две разные вещи, и путать их дорого.

**Дедупликация на стороне рантайма** — `WithEventIdempotencyKey`. Защищает от двойной **публикации**: две публикации с одним ключом рантайм схлопнет в одно событие. Повтор — успех, и `Publish` возвращает id исходного события.

**Идемпотентность обработчика** — ваша. Защищает от повторной **доставки**, которая при at-least-once случится в любом случае. Ключ дедупликации на стороне потребителя обычно строится из идентификатора события или из доменного ключа в payload'е:

```go
func handlePlacedOnce(ctx context.Context, e *orderpb.OrderPlaced) error {
	inserted, err := insertIfAbsent(ctx, "receipt:"+e.GetOrderId())
	if err != nil {
		return err
	}
	if !inserted {
		return nil // уже обработано, подтверждаем доставку
	}
	return sendReceipt(ctx, e.GetOrderId())
}
```

## 8. Ключ партиции и порядок

Без ключа партиции доставки обрабатываются параллельно — требования порядка у них нет.

С ключом события выстраиваются в последовательную цепочку: следующая доставка с тем же ключом не начнётся, пока не закончится предыдущая. На стороне публикации порядок ключа тоже держится: в одной пачке к рантайму едет не больше одного события на ключ, следующее ждёт следующей пачки.

Цена очевидна: ключ партиции — это сериализация. Один медленный обработчик задерживает всю дорожку. Берите ключ настолько мелкий, насколько позволяет домен: `orderID`, а не `"orders"`.

## 9. Без ожидания

```go
func publishMetric(ctx context.Context, c *sb.Client) error {
	_, err := sb.PublishEvent[*orderpb.OrderPlaced](ctx, c, "order.placed",
		&orderpb.OrderPlaced{OrderId: "o-3"},
		sb.WithFireAndForget())
	return err
}
```

`WithFireAndForget` возвращает id сразу после постановки в очередь и не ждёт подтверждения рантайма. Цена — возможная потеря: пока рантайм не подтвердил событие, оно живёт только в памяти процесса и умирает вместе с ним, а сбой доставки только пишется в лог. Полная очередь отказывает и здесь (`CodeQueueFull`).

Осмысленно для телеметрии и аналитики, у которых потеря отдельного события дешевле задержки. Для всего, что влияет на состояние домена, — нет.

## 10. Очередь публикаций

| Параметр | По умолчанию | Опция |
|---|---|---|
| Размер очереди | `10000` событий | `WithMaxPendingPublishes(n)` |
| Предел одной публикации от постановки до подтверждения | `30s` | `WithPublishTimeout(d)` |

**Переполнение.** На пределе `PublishEvent` сразу возвращает `CodeQueueFull`; уже накопленное не выбрасывается. Ошибка ретраебельная: `Retryable()` истинен.

**Таймаут.** Если подтверждения нет за `WithPublishTimeout`, публикация возвращает `CodeTimeout`, и сообщение говорит, было ли событие вообще отправлено. Неотправленное событие уходит из очереди. Отправленное могло дойти до рантайма — повторять его безопасно только с `WithEventIdempotencyKey`. Отмена `ctx` действует так же.

**Отправитель.** Одна пачка в полёте, до 100 событий. Транспортный сбой или ответ без вердикта возвращают пачку в очередь под теми же id; паузы между повторами — 100 мс, 250 мс, 500 мс, 1 с, 2 с, 5 с, последняя повторяется, успех сбрасывает лестницу. После переподключения отправитель пробует сразу.

**Вердикты рантайма:**

| Вердикт | Результат `PublishEvent` |
|---|---|
| принято | id события |
| дубликат (тот же ключ идемпотентности) | успех, id исходного события |
| конфликт (тот же id с другим содержимым) | `CodeConflict` |
| невалидное имя | `CodeInvalidEventName` |
| запрещено политикой | `CodeAccessDenied`, и срабатывает `OnPolicyViolation` |
| нет вердикта, транспортный сбой | повтор с тем же id |

**Отказ политики доходит до владельца** и через колбэк — это удобно для `WithFireAndForget`, где ошибку вернуть уже некому:

```go
func watchViolations(c *sb.Client) {
	c.OnPolicyViolation(func(v sb.PolicyViolation) {
		log.Printf("policy refused %s %q: %s", v.Declaration, v.Value, v.Reason)
	})
}
```

Для публикации `Declaration` будет `"event.publish"`, `Value` — имя события, `DenySide` — `"self_egress"`.

**Остановка.** `Stop` досылает очередь в пределах своего дедлайна; что не успело уйти, завершается `CodeConnection` «client stopped».

## 11. DLQ

Dead-letter-очередь принадлежит рантайму. API для неё в SDK нет — повторная доставка и разбор делаются в дашборде на `:14444`.
