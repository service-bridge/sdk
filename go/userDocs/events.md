# Events

[← к индексу](./index.md)

## 1. Краткая модель

```
publish                                    deliver
────────                                   ────────
sb.PublishEvent → локальный SQLite         рантайм → стрим Subscribe
       ↓ (фон)                                      ↓
   дренаж → Events.Publish в рантайм       обработчики → ack / nack
```

Публикация **возвращается быстро и не ходит в сеть**. Недоступный рантайм не имеет права ни замедлить публикацию, ни провалить её. Из этого следует главное: возврат `Publish` без ошибки означает «событие записано на диск», а не «событие доставлено».

## 2. Объявление события

```go
func declarePlaced(c *sb.Client) (*sb.Event[*orderpb.OrderPlaced], error) {
	return sb.DefineEvent[*orderpb.OrderPlaced](c, "order.placed")
}
```

`DefineEvent` объявляет событие, которое сервис публикует, и замораживает его схему — она выводится из protobuf-дескриптора типа. Возвращённый `*sb.Event[T]` — типизированная ручка публикации.

Объявлять нужно **до** `Start`; позже — `CodeState`.

### Имя события

Имя должно подходить под `^[a-z0-9_-]+(\.[a-z0-9_-]+)*$` — сегменты из строчных букв, цифр, подчёркиваний и дефисов, разделённые точками. Правило то же, что у рантайма, и проверяется локально: неподходящее имя отвергается при объявлении с `CodeInvalidEventName`, а не после круга по сети.

Подстановочные знаки в **публикуемом** имени недопустимы — публикуется всегда конкретное событие.

## 3. Подписка

```go
func subscribeShipped(c *sb.Client) error {
	return sb.SubscribeEvent(c, "order.shipped",
		func(ctx context.Context, e *orderpb.OrderShipped) error {
			return handleShipment(ctx, e.GetOrderId(), e.GetCarrier())
		})
}
```

Тип события выводится из функции. Подписываться нужно до `Start`.

Несколько обработчиков на одно имя допустимы: они выполняются в порядке регистрации, и первая же ошибка отклоняет всю доставку — обработчики после упавшего не выполняются.

### Шаблоны

Подписка, в отличие от публикации, принимает шаблон:

```go
func subscribeFamily(c *sb.Client) error {
	return sb.SubscribeEvent(c, "order.*",
		func(ctx context.Context, e *orderpb.OrderPlaced) error {
			return audit(ctx, e.GetOrderId())
		})
}
```

| Знак | Что покрывает |
|---|---|
| `*` | ровно один сегмент |
| `#` | ноль или больше сегментов |

Маршрутизацией занимается рантайм: он матчит имя опубликованного события против шаблонов подписчиков. SDK дополнительно сопоставляет шаблон локально, когда выбирает обработчики для пришедшей доставки, — без этого подписка на семейство регистрировалась бы на сервере, доставки приходили бы, а локальный поиск по точному имени их бы не находил.

Доставка несёт **конкретное** имя, которое использовал публикующий. Обработчик получает уже декодированный payload; если под шаблон попадают события с разной формой payload'а, декодирование в один тип неминуемо сломается — для такого случая есть `sb.SubscribeEventRaw`.

### Недекодированный payload

```go
func subscribeRaw(c *sb.Client) error {
	return sb.SubscribeEventRaw(c, "audit.#",
		func(ctx context.Context, payload []byte) error {
			return archive(ctx, payload)
		})
}
```

Это способ обслужить имя, у которого форма payload'а зависит от публикующего, — ни один параметр типа такое не описывает.

### Событие, на которое никто не подписан

Доставка, для которой не нашлось ни одного обработчика, **подтверждается**, а не отклоняется. Маршрутизация принадлежит рантайму; событие, дошедшее до сервиса, у которого нет обработчика на это имя, исчерпано, и отклонение заставило бы доставлять его снова и снова.

## 4. Публикация

Публиковать можно только **после** `Start` — до него локального буфера ещё нет, и попытка вернёт `CodeState`.

```go
func publishPlaced(ctx context.Context, placed *sb.Event[*orderpb.OrderPlaced]) (string, error) {
	return placed.Publish(ctx,
		&orderpb.OrderPlaced{OrderId: "o-1", Total: 4200, UserId: "u-1"},
		sb.WithPartitionKey("o-1"),
		sb.WithEventIdempotencyKey("order-o-1-placed"),
	)
}
```

Возвращается идентификатор события (UUIDv7).

Без объявленной ручки — то же самое свободной функцией:

```go
func publishDirect(ctx context.Context, c *sb.Client) (string, error) {
	return sb.PublishEvent[*orderpb.OrderPlaced](ctx, c, "order.placed",
		&orderpb.OrderPlaced{OrderId: "o-2", Total: 900, UserId: "u-2"})
}
```

## 5. PublishOption

| Опция | По умолчанию | Что делает |
|---|---|---|
| `WithEventIdempotencyKey(k)` | нет | Ключ дедупликации на стороне рантайма. Назван отдельно от `WithIdempotencyKey`, потому что эти два ключа едут в разные места. |
| `WithPartitionKey(k)` | нет | FIFO-дорожка: события с одним ключом видны потребителям в порядке публикации. |
| `WithFireAndForget()` | выключено | Отправка сразу в рантайм, мимо локального буфера и всех ретраев вместе с ним. |
| `WithHeaders(map[string]string)` | нет | Метаданные конверта. |
| `WithOccurredAt(unixMs)` | момент публикации | Когда событие произошло, в unix-миллисекундах. |

## 6. Гарантии доставки

**At-least-once.** Обработчик обязан быть идемпотентным.

- Возврат `nil` из обработчика подтверждает доставку.
- Возврат ошибки отклоняет её, и рантайм доставит событие позже.
- Паника обработчика превращается в отклонение с причиной, а не роняет процесс.
- Ретраи, веерная рассылка и dead-letter — за рантаймом.

Одновременно обрабатываемых доставок не больше `WithMaxInFlightEvents(n)` (по умолчанию 32). Это настоящий backpressure: на пределе SDK перестаёт вычитывать стрим доставок, и рантайм это чувствует.

Контекст обработчика несёт трассировку публикующего, поэтому вызовы изнутри обработчика попадают в то же дерево трейса. Он же отменяется при остановке клиента: обработчик, игнорирующий отмену, держит `Stop` ровно столько, сколько работает.

## 7. Идемпотентность

Две разные вещи, и путать их дорого.

**Дедупликация на стороне рантайма** — `WithEventIdempotencyKey`. Защищает от двойной **публикации**: две публикации с одним ключом рантайм схлопнет в одно событие.

**Идемпотентность обработчика** — ваша. Защищает от повторной **доставки**, которая при at-least-once случится в любом случае. Ключ дедупликации на стороне потребителя обычно строится из идентификатора события или из доменного ключа в payload'е:

```go
func handlePlacedOnce(ctx context.Context, e *orderpb.OrderPlaced) error {
	inserted, err := insertIfAbsent(ctx, "receipt:"+e.GetOrderId())
	if err != nil {
		return err
	}
	if !inserted {
		return nil // уже обработано, подтверждаем доставку
	}
	return sendReceipt(ctx, e.GetOrderId())
}
```

## 8. Ключ партиции и порядок

Без ключа партиции доставки обрабатываются параллельно — требования порядка у них нет.

С ключом события выстраиваются в последовательную цепочку: следующая доставка с тем же ключом не начнётся, пока не закончится предыдущая. Рантайм гарантирует не больше одной доставки «в полёте» на пару (потребитель, ключ), но доставки приходят асинхронно, поэтому очередь дополнительно держится локально.

Цена очевидна: ключ партиции — это сериализация. Один медленный обработчик задерживает всю дорожку. Берите ключ настолько мелкий, насколько позволяет домен: `orderID`, а не `"orders"`.

## 9. Без ожидания

```go
func publishMetric(ctx context.Context, c *sb.Client) error {
	_, err := sb.PublishEvent[*orderpb.OrderPlaced](ctx, c, "order.placed",
		&orderpb.OrderPlaced{OrderId: "o-3"},
		sb.WithFireAndForget())
	return err
}
```

`WithFireAndForget` отправляет конверт прямо в рантайм, минуя локальный буфер. Вместе с буфером теряются и ретраи: не доехало — значит потеряно.

Осмысленно для телеметрии и аналитики, у которых потеря отдельного события дешевле задержки. Для всего, что влияет на состояние домена, — нет.

## 10. Локальный outbox

Буфер лежит в файле `sdk.db` внутри каталога данных: по умолчанию `./.servicebridge/sdk.db`, меняется через `WithDataDir`. Драйвер SQLite — чисто на Go, cgo не нужен.

| Параметр | По умолчанию | Опция |
|---|---|---|
| Каталог данных | `./.servicebridge` | `WithDataDir(dir)` |
| Предел буфера | `10000` строк | `WithMaxOutboxRows(n)`; `0` снимает предел |
| Размер пачки дренажа | `100` | `WithDrainBatchSize(n)` |

**Переполнение.** На пределе `Publish` возвращает `CodeOutboxFull`, и строка не пишется — ничего из уже накопленного не выбрасывается. Снятый предел превращает долгую недоступность рантайма в заполненный диск, поэтому по умолчанию он есть.

**Недоступность рантайма ничего не хоронит.** Лестница повторов дренажа — 1 с · 5 с · 30 с · 2 мин · 10 мин с джиттером; последняя ступень повторяется бесконечно. Это ограничитель темпа, а не бюджет попыток: публикация уже вернула успех и пообещала durability, поэтому «кончились попытки» для транспортного сбоя не бывает.

**Терминальны только осмысленные вердикты** по конкретному конверту: имя, которое рантайм считает невалидным, и запрет политикой доступа. Такая строка помечается провалившейся и больше не повторяется.

**Отказ политики доходит до владельца.** Публикация вернулась задолго до отправки, бросать ошибку уже некуда, поэтому отказ едет в лог уровня Warn и в колбэк:

```go
func watchViolations(c *sb.Client) {
	c.OnPolicyViolation(func(v sb.PolicyViolation) {
		log.Printf("policy refused %s %q: %s", v.Declaration, v.Value, v.Reason)
	})
}
```

Для публикации `Declaration` будет `"event.publish"`, `Value` — имя события, `DenySide` — `"self_egress"`.

**Переживание рестарта.** Строки, оставшиеся в состоянии «в полёте» после падения процесса, при открытии буфера возвращаются в очередь. Доставленные удаляются в той же транзакции, что и результат отправки пачки, — накопления мусора нет. А вот строки, помеченные провалившимися терминально, остаются в файле: их никто не убирает, они существуют как след для разбора.

## 11. DLQ

Dead-letter-очередь принадлежит рантайму. API для неё в SDK нет — повторная доставка и разбор делаются в дашборде на `:14444`.
