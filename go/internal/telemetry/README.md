# telemetry

## Зона ответственности

Ядро телеметрии Go SDK: контекст трассировки в `context.Context`, формат заголовка `X-SB-Trace`, четыре кольцевых буфера с байтовыми бюджетами и жизненный цикл операции (кадры START/END) вместе с захватом payload'ов по режиму, который пушит рантайм.

Не делает: не открывает gRPC-стрим и не отправляет батчи (это транспорт), не агрегирует метрики, не перехватывает `slog`, не решает, какие операции эмитить — это делают вызывающие домены по матрице владения.

## Архитектурные решения и почему

**Контекст передаётся явно.** В Node-SDK трассировка живёт в `AsyncLocalStorage`, и это стоило трёх отдельных проблем: единственность экземпляра при сборке бандла, отсутствие проброса через продолжения async-генератора, отдельный путь для хук-фреймворков. В Go таких проблем нет — `context.Context` идёт параметром, и это единственный носитель, который однозначно переживает границу горутины. Ambient-хранилища здесь нет и не будет.

**Битый `X-SB-Trace` — это новое дерево, а не ошибка.** Разбор строгий (длина 73, разделитель по позиции 36, обе половины — валидные UUID), но любое отклонение молча порождает корневой трейс (ADR-0006 §6). Разделитель ищется по позиции, потому что UUID сами содержат дефисы. Пара «разбор + формат» в SDK ровно одна (ADR-0006 §7) и зеркалит `runtime/internal/telemetry/header.go`.

**Ошибка генерации UUID пробрасывается.** Подстановка `uuid.Nil` слила бы независимые трейсы в одно дерево на стороне рантайма, а это молчаливая порча данных. Сбой источника энтропии виден вызывающему.

**Peek без удаления + commit по идентификаторам.** Элемент уходит из кольца только после подтверждения рантайма — именно это даёт at-least-once при переподключении стрима. Непорченный батч возвращается следующим `Peek` в том же порядке.

**Кольцо на индексах, а не сдвиг массива.** Вытеснение и подтверждение помечают слот мёртвым на месте; мёртвый префикс срезается сразу, дыры от подтверждения вразнобой убирает амортизированная перепаковка. Сдвиг массива (как в Node) деградирует линейно ровно под насыщением — то есть тогда, когда это важнее всего. Тест `TestRingStaysAmortizedUnderSaturation` фиксирует это через счётчик перемещений слотов.

**Оценка размера приблизительная, но полная.** Точная сериализация на горячем пути дороже, чем пара процентов недобранного бюджета: число нужно только чтобы ограничить рост буфера. При этом считается всё, что реально занимает память — в Node метки метрики не учитывались, и кольцо тихо перерастало объявленный бюджет.

**`meta_json` и `attrs_json` по умолчанию — `{}`.** Рантайм превращает пустой буфер в SQL NULL, а обе колонки `NOT NULL`. Кадр START всегда несёт валидный JSON-объект; кадр END — дельта, и эти поля в нём пустые.

**Ретрай мутирует ту же операцию.** Один логический вызов — одна строка (ADR-0001); счётчик попыток едет в кадре END. `End` идемпотентен: первый вызов фиксирует статус, повторные ничего не делают.

**Матрица владения.** `RPC.CALL` эмитит только вызывающий SDK (одна строка на логический вызов), `HTTP.HANDLE` и `USER.SUBOP` — SDK. `EVENT.PUBLISH`, `EVENT.DELIVER`, `WORKFLOW.RUN`, `JOB.EXEC` принадлежат рантайму, SDK их не дублирует.

**Рантайм — единственный источник истины по захвату.** Режимы приходят пушем через стрим реестра; переопределение хендлера умеет только сужать (`none < errors < all`), иначе прикладной код мог бы публиковать payload'ы, которые оператор выключил. До первого снапшота: все каналы `none`, лимит 65536, телеметрия включена — операции репортятся (из них строится карта сервисов), payload'ы — нет.

**Дешёвая проверка режима до сериализации.** `Recorder.Capturing` и `Op.Capturing` отвечают, имеет ли смысл вообще готовить payload. В Node тела сериализовались до проверки режима, и на дефолтной конфигурации каждый запрос платил полную сериализацию в мусор.

**Захваченный payload копируется.** Вызывающий владеет своим буфером и волен его переиспользовать; то, что переживает вызов (буфер режима `errors` или элемент кольца), копируется один раз в момент захвата.

**Метрики агрегируются, а не льются точкой на вызов.** В Node каждый `inc()` клал отдельную точку в кольцо на 16 KiB, и сервис на 1000 rps молча терял большинство метрик: единственным признаком был растущий счётчик потерь. Здесь состояние копится по серии и выгружается раз в окно. Ключ серии собирается с непечатным разделителем — печатный подделывается значением метки, и две разные серии сливаются в одну.

Gauge **сохраняет значение между окнами, но переэмитится только после нового `Set`.** Переотправка неизменного gauge каждые 250 мс — это четыре точки в секунду на серию без новой информации, ровно тот объём, ради устранения которого агрегация и вводилась. Рантайм хранит сырые точки, поэтому последнее записанное значение читается весь срок хранения. Счётчики и гистограммы после выгрузки обнуляются.

**Транспорт читает за пределами неподтверждённого префикса.** Рантайм подтверждает по тикеру раз в две секунды, а не на каждую пачку. В Node неподтверждённые элементы оставались в голове кольца, и `Peek`, ограниченный размером пачки, возвращал только их — между подтверждениями не отправлялось ничего.

**Граница честности подтверждений.** `TelemetryAck` не несёт идентификатора пачки, поэтому ни одно подтверждение не может назвать, что именно оно подтверждает. Каждый записанный элемент помечается эпохой, в которую он ушёл, и эпоха освобождается только подтверждением, поднявшим счётчик на две — то есть с отставанием на одно полное подтверждение. Освобождать текущую эпоху нельзя: элементы, записанные циклом, который разминулся с подтверждением в пути, исчезли бы из буфера, так и не дойдя. Цена — лишний интервал занятости буфера и окно повторной доставки того же размера; и то, и другое допустимо при at-least-once.

**Затор не приводит к паузе.** Уровень фиксируется и доступен наблюдателю, и только. Пауза флашера вытесняет старейшие кадры, а старейшие — это кадры начала операции: рантайм получил бы конец без начала.

**`process.rss_bytes` считается как `MemStats.Sys - HeapReleased`, а не как RSS ядра.** Переносимого способа взять текущий RSS в стандартной библиотеке нет, а `getrusage` отдаёт только максимум за время жизни процесса, который никогда не падает. Имя метрики совпадает с Node, потому что графики консоли читают именно его.

## Зависимости

Опирается на:
- `internal/pb/servicebridge/v1` — типы `OpReport`, `Log`, `MetricPoint`, `PayloadAttachment`, `Channel`, `Status`, `CaptureMode`, `CaptureModes`.
- `internal/stream` — супервизор жизненного цикла для стрима `Telemetry.Report`.
- `github.com/google/uuid` — генерация и разбор UUIDv7.
- `google.golang.org/grpc/metadata` — перенос заголовка в метаданных вызова.

Опираются на него:
- транспорт телеметрии — берёт батчи через `Ring.Peek`, подтверждает через `Ring.Commit`, читает `Policy.Enabled`;
- сбор метрик и мост `slog` — кладут точки и записи через `Ring.PushMetric` / `Ring.PushLog`;
- домены RPC, HTTP и пользовательских под-операций — стартуют и закрывают операции через `Recorder`;
- слой реестра — источник снапшота `CaptureModes`, который кладётся в `Policy.Set`.
